# PCAG Studio first release candidate: documentation and playable adventure

* **Author:** Gogodr
* **Date:** 2026-11-02

## Overview

Replace the dated product and developer guidance outside `docs/design` with documentation checked against the current working tree and a development plan for the first release candidate (RC). The RC is a technical, JavaScript-authored Electron Studio that exports an unsigned game-project ZIP. The ZIP contains the game content, Electron player source, and a script that installs pinned build dependencies and builds a local desktop game. Studio itself is signed by PCAG; creators sign any games they distribute under their own identity. The RC must let an author build, preview, save, reopen, export, locally build, and play a reusable five-scene adventure. Studio must provide a Landing Screen section to set its background; the built game's landing screen presents New Game, Load Game, and Settings. Visual node scripting, a visual dialogue builder, and website export with accounts and database-backed saves remain later work. The longer-term goal of programming-free authoring remains separate from this RC gate.

The acceptance story has five scenes: a puzzle opens the first door; an NPC conversation enables an element and then a second door; the player backtracks to scene 2 and returns without losing state, collects A, uses A to reveal B while keeping A, collects B, combines A and B into C, then uses C to open the next door; a first-arrival cinematic moves the protagonist and NPC through alternating speech with controls locked, then opens a door; and the final scene ends the adventure. Closing the game before the cinematic finishes must cause it to replay on return from the latest save. After completion, revisiting that scene must be interactive without replay. These behaviors must work through general engine features, not story-specific branches.

## Analysis

The [development plan](docs/planning/06-development-plan.md) calls for declarative rules, a classic verb bar, and no arbitrary code in imported projects. The proposed RC instead uses JavaScript events and a contextual cursor. The new documentation must explicitly state the narrower RC scope, what the previous requirements become, and which user-accepted milestones remain historical evidence. It must not silently mark later backlog items accepted because parts of them exist in code. The [validation log](docs/development/validation-log.md) records focused checks and F01-F06 acceptance; it does not establish RC acceptance.

The [current-state review](docs/planning/10-current-state.md), dated 2026-10-30, says the player has no walking protagonist and that scene element properties are read-only. Current runtime and editor code, plus later validation-log entries, show newer behavior. Even the README and roadmap disagree about F06 status. Therefore, replacing text requires a dated capability inventory with links to source and verification. Each claim should be labeled **implemented**, **focused-tested**, **integrated-tested**, **user-accepted**, or **planned**. Treat the dirty working tree as the inspected source snapshot, not a released baseline. Run a fresh integrated gate only after the relevant changes are frozen.

Deleting every document outside `docs/design` in one pass would erase decision history, setup instructions, format details, acceptance evidence, and links from the README and sprite-tool READMEs. Inventory every file and incoming link first. Extract still-relevant facts and dated acceptance evidence into new documents, then delete the old files as requested. Git history remains the archive of the old wording. Give each current fact one owner: current capabilities, project format, player controls, desktop packaging, save behavior, RC scope and plan, release validation, and historical decisions. Update incoming links and keep `docs/design` intact. ### The main missing feature is one durable game session

The current [project model](packages/project-format/src/index.ts) has rooms, elements, characters, SceneState, GameState, events, and initial element actions, but no item catalog or player-save format. The [runtime](packages/runtime/src/index.ts) mounts the starting room and creates session defaults at mount. Its events and player character are bound to that room; disposing closes and destroys it. The [browser shell](apps/player/src/app/startPlayer.ts) mounts that runtime once and shows stage, status, observation, hint, and debug controls. It has no landing screen, inventory, menu, slots, room transition, or ending. These are implementation gaps, even though movement, event dispatch, cursor cycling, and script-driven state already exist.

The RC needs a game-session owner independent of Phaser, React, Electron, and file storage. It should own active scene, protagonist location, GameState, per-scene SceneState, per-scene element changes, inventory, and durable cinematic completion. Scene enter/leave must select the destination's events and actor, preserve prior scenes, and define the order of close/load triggers. Preview and exported player must use the same commands and transition rules. Closing the Electron game mid-sequence must not commit unfinished effects. A saved snapshot must restore before scene-load triggers run, with a rule preventing duplicate effects.

Project definitions, editor workspace values, live session values, and player saves are distinct. Existing state variables have both `value` and `defaultValue`; runtime starts from defaults. The RC must name the role of each value and avoid serializing editor current values as player progress. A separate, versioned save contract should record stable game/project identity and content compatibility, slot identity, scene and position, all durable state, inventory, element changes, and cinematic completion. Each slot has its own local save file. The preferred location is a `save` folder in the exported game's distribution root; the game tests that location before using it and falls back to an OS-specific writable app-data folder when necessary. Starting New Game creates a fresh run and leaves existing manual slots intact. A later manual save writes the selected slot, while autosave overwrites only the reserved autosave slot. Save and load need atomic write or last-good recovery, corruption/version messages, and behavior when authored IDs change. The author chose a reserved autosave slot that updates after every completed scene change while autosave is enabled in player settings. Cinematic completion changes a SceneState flag in memory but does not autosave by default; an author may call an explicit autosave command from the cinematic script after completion. If the player closes after completion but before another save or scene change, loading the autosave restores the earlier checkpoint and replays the cinematic. The plan must define the transition checkpoint and handle save failures without corrupting the previous slot. This policy does not preserve every action between scene changes unless the player saves manually. Updates must not overwrite either save location, and the chosen location must be visible to the player.

For desktop packaging, the preferred `game/save` folder means the exported distribution root beside the launcher, never inside a macOS `.app` bundle. The plan must name the actual Windows, Linux, and macOS fallback paths; do not assume Windows LocalLow is Electron's default `userData` location. A stable game ID and a persisted/discoverable location choice must prevent saves from vanishing when permission, installation path, or writeability changes. If both preferred and fallback locations contain slots, show or reconcile them without silently choosing one. Test extraction, installation, relocation, update, and read-only folders. Writes must replace a slot atomically or preserve its last good copy; a failed save must not be reported as success.

The chosen automatic trigger is a completed scene change while autosave is enabled. The plan must settle whether turning autosave on writes immediately or waits for the next scene change, whether New Game creates an initial checkpoint, the exact scene-close/load ordering captured by transition autosave, and whether a scripted autosave is allowed only after cinematic completion. Toggling autosave off should leave the previous slot intact unless the author chooses a different rule. The UI should show the last *saved* checkpoint: a cinematic can be complete in memory yet replay after loading an older save.

### Script effects and the cinematic need one commit boundary

The existing [script worker](packages/runtime/src/scene-script.worker.ts) executes authored JavaScript with `new Function`. It has worker global capabilities; the worker and timeout do not make imported scripts safe. The author chose this RC trust rule: when a `.pcag` archive contains scripts, import asks whether to trust the author and load the scripts or skip them; a project opened from a local folder is trusted directly. Skipped scripts stay in the imported project but are disabled. Studio must make disabled scripts visually obvious and let the creator later inspect and trust-enable each script or delete and replace it. Detection and disabling must happen before any script runs. The plan must define how preview/export handle disabled scripts and how their status persists in project files. It must also define the supported script API, errors, cancellation, ordering, and available capabilities. Existing scripts receive `scene`, `game`, and `trigger`; new item, dialogue, navigation, speech, and sequence commands should extend a stable, validated contract. Scripts must not directly own renderer or storage. The import prompt is a trust decision, not a technical sandbox.

The archive must be decoded within size and extraction limits, then inspected for scripts before workspace activation, preview, scene-load triggers, or export execution. Script bytes and the disabled flag must survive import, save, reopen, and export; a disabled script must remain disabled in the exported game. The prompt should identify source and consequence, including worker network capabilities. The chosen rule trusts local folders directly, so someone can extract an untrusted archive and open that folder to bypass the prompt. Document this residual risk and decide separately whether unknown-origin folders need a warning; do not describe the archive prompt as universal protection.

Current scripts validate state after completion, yet an awaited animation command can apply an element change before later code fails. That can leave a partial effect. The RC must decide which effects are transactional and which are committed steps, report partial failure, and test retry behavior. The first-arrival cinematic specifically needs a single controller: lock all world and inventory input, run ordered actor/NPC movement and alternating speech, commit the door opening and completion flag together only after the final beat, and unlock on completion or recoverable error. Player menu controls, manual save, and skip remain locked during playback; the UI must show why. An interrupted sequence with no completion commit replays from the last save; a completed in-memory revisit does not. Repeated triggers and queued position events must not start duplicate sequences. Existing worker timeouts, dispatch budget, and event coalescing need visible diagnostics and tests for a realistic cinematic length.

The author chose to lock player menu controls during the cinematic, so manual save and skip are unavailable then. A scripted autosave, if used, must occur after the last beat and the atomic door/completion commit. The plan must specify OS window-close behavior during a sequence or pending write, a total sequence duration bound, cancellation of transient movement/speech, and the response to partial worker failure. A completed in-memory revisit stays interactive; loading a pre-completion save replays the sequence. Show the last persisted checkpoint so players understand that closing before another save can replay a scene they watched to completion.

### Authoring and player controls must meet at one command API

The inspector currently stores initial `availableActions`; scripts need a validated way to change the live set and refresh cursor/hint state. The current action list has `move_to` but no `pick_up`, while older player requirements include Pick up and distinguish Walk. Resolve that vocabulary and migrate older action arrays. Define stable item IDs, scene element IDs, inventory ownership, duplicate pickup behavior, and atomic add/remove/combine rules. For the acceptance story, using A on the scene element keeps A and reveals B; combining A+B produces C with an explicit consume/retain rule. Repeated or canceled actions must not duplicate items or change world state. Physical actions should obey arrival and revalidation rules where promised by existing character requirements.

Use one typed command path for cursor clicks, wheel selection, inventory targeting, keyboard actions, dialogue, and menu actions. Specify precedence and cancellation for hovering an element, walking on ground, selecting an inventory item, opening dialogue or menu, and cinematic lock. The bottom text should describe the pending action consistently. Inventory opens from its top-right button or `I`; the adjacent menu button and `Esc` open the same menu. Save/load slots and the Exit prompt must distinguish player progress from creator project saving. Exit prompts to save, then returns to the landing screen. The landing screen offers New Game, Load Game, and Settings, including volume and autosave on/off. Dialogue is authored in JavaScript for this RC, but authors still need documented trigger arguments, choice/speaker/response behavior, conditions, repeat visits, and actionable script errors in preview and export.

Use distinct names for Studio's welcome screen, its Landing Screen editor section, and the exported game's title screen. The Exit prompt needs save, exit without saving, and cancel outcomes; define the slot selected for Save and keep the session active if a write fails unless the player explicitly chooses otherwise. Define how Load displays slot labels, timestamps, scene, and last checkpoint, and whether an unsaved run survives return to title. These are new lifecycle screens, not overlays on the current one-room player shell.

### Compatibility, qualification, and diagnostics are release work

The project reader currently accepts `schemaVersion: 1` and rejects unknown fields or other versions. Items, action changes, and new event data need an explicit authored-schema version or an equally explicit v1 extension rule. The plan should choose one, define old-project normalization and reference diagnostics, preserve source files through migration, and keep the archive envelope distinct from the nested project schema. Preview and exported player must receive compatible project and runtime versions. New save versions should not overwrite saves a previous player can still read; unsupported future versions should fail clearly. Test import/export and rollback, including an interrupted migration and changed item/scene IDs.

This is a local desktop creator and exported desktop game. Cloud throughput, database load, and LLM tokens are not relevant RC limits. Relevant limits are script CPU/queue time, asset and archive size, graphics memory, save-folder permissions, and disk space. The plan should measure representative bounds and show clear failure messages. Offline diagnostics should include scene/event/trigger IDs, phase, script location, timeout or validation category, and the last safe save checkpoint. A local reproduction trace is more useful here than remote telemetry; exclude authored dialogue and personal paths by default.

Keep a bounded local trace with game/build/schema/save versions, a play-session ID, event and trigger IDs, transition phase, queue or timeout category, save target and write result, and last safe checkpoint. Give players an accessible copy/export action. Omit script bodies, dialogue, and absolute personal paths by default. Measure package size and disk headroom as well as archive expansion and representative five-scene memory use.

The RC gate should include the five-scene story in creator preview and a locally built, independently launched Electron game from the exported ZIP, plus a second small fixture to prove reuse. The ZIP contains a versioned, rebuildable, unsigned game project and a build script that installs pinned build dependencies. Repeatable source contents and recorded inputs are required; bit-for-bit identical OS executables are not claimed without evidence. The plan must identify those dependencies, their lockfile and source, build prerequisites, network needs, and exact output folder. Players of the locally built game should not need Node, npm, Python, or a developer checkout; creators who build it locally do need a documented toolchain and possibly network access. Windows, Linux, and macOS are all RC targets for Studio and game builds. Electron shares application code across them but still needs separate Studio packages and target-specific game build/launch qualification. Exercise project close/reopen, export/import, all scene returns, save/load across app closure, corrupt or incompatible slot files, interrupted cinematic at multiple beats, completed revisit, script failure, keyboard/menu access, and both preferred and fallback save-folder permissions. The plan must declare OS versions and CPU architectures actually tested; untested combinations remain unclaimed. Stage schema/session, scene navigation, items/actions/dialogue, cinematic, save/UI, desktop export, and qualification in buildable increments, with exact file boundaries and tests at each step.

The current [exporter](packages/project-io/src/browser.ts) creates only a static browser ZIP; [package.json](package.json) has no Electron packager and lists Electron as a development dependency. Its root lockfile covers Studio and game dependencies together, so copying it alone would not define an isolated game build. Studio's [main process](apps/creator/electron/main.cjs) invokes system Python and repository-relative animation code. Desktop export therefore needs a new source-project packaging path, not a renamed browser ZIP. Build signed Studio artifacts for each claimed OS and CPU architecture. Export one portable game-project ZIP whose local build script produces an unsigned Electron game for the creator's current target; specify pinned dependencies, build host requirements, offline or network behavior, output layout, and how the creator supplies their own signing credentials later. The built game should bundle Electron and its runtime so players need no build tools. Studio's Python/OpenCV/NumPy/Pillow animation workflow needs its own bundled-versus-installed choice and per-platform tests. The game must not inherit that Studio-only dependency.

The game-project ZIP needs a versioned manifest binding game ID, authored schema, player/runtime version or hash, file inventory and checksums, game-specific `package.json` and lockfile, supported build targets, and output layout. It must include validated project data, every referenced asset, player renderer and Electron main/preload source or compiled inputs, build and packaging configuration, platform metadata/icons, license notices, and a README with target-specific commands. The build must work from a clean extraction without Studio, checkout paths, or PCAG secrets. Validate missing assets, mismatched versions, and unsafe archive paths before dependency installation. Specify Node/npm versions, registry and integrity policy, a clean lockfile-based install command, packager version, network/cache/offline behavior, host permissions, exact output paths, and launch commands on each OS. Test script invocation after ZIP extraction on Linux/macOS because the current ZIP writer does not preserve POSIX executable mode; instructions may need to call a shell explicitly. Record source ZIP hashes and build inputs; an unsigned binary may still vary by OS and build environment.

The `.pcag` trust prompt controls authored runtime scripts, not the exported ZIP's install/build script, npm lifecycle scripts, or downloaded packages. Those scripts run with the creator's host privileges. Export and extraction must not auto-run them. Studio and the ZIP README must show the exact command and its trust consequence, including dependency source, before the creator executes it. Keep PCAG signing credentials out of exported files, local build defaults, environment capture, and diagnostic logs. Creator signing is a distinct, creator-initiated step after the unsigned build. An exported ZIP containing retained disabled scripts must preserve their bytes and disabled flags, and the built game must still skip them; missing required behavior should produce a validation warning instead of silently failing in play.

Only Studio is signed by PCAG. The author chose Azure Artifact Signing for the Windows Studio build, subject to confirming Public Trust eligibility and account access. For macOS Studio, the proposed path is an Apple Developer ID Application signature, hardened runtime, and notarization. For Linux Studio distribution, the proposed path is an OpenPGP signature and published checksum for its release archive; a future AppImage may use an embedded signature. Exported game-project ZIPs and locally built games remain unsigned by PCAG. Each game creator is responsible for signing their own distributed build. The Studio docs should explain that signing is a separate creator step and must not silently use PCAG credentials for user-authored scripts.

Studio release packaging/signing, unsigned game-project export, and a creator's local build must have separate entry points, configuration, and credential scopes. PCAG signing runs only in a trusted Studio release job from checked source, never from imported project data or the export builder. Verify the Studio signature or Linux release signature/checksum on each target and verify that the ZIP and game output carry no PCAG signature or secret. Windows Azure eligibility is an explicit Studio release gate; if unavailable, the signed Windows RC claim needs a new decision rather than a silent unsigned substitution. The export UI and docs should label each artifact's trust status: PCAG-signed Studio, unsigned project ZIP, unsigned local game, and creator-signed distributed game. Linux archive signature and Windows/macOS app signing are different mechanisms, so describe them separately.

Prove a clean ZIP extraction, local game build, and independent launch on one target early, before save paths and content format depend on output layout. The final gate must build from exported ZIPs on Windows, Linux, and macOS, then run the unsigned game packages with declared OS/architecture versions, preferred/fallback save tests, relocation/update, trust-skip import round trips, cinematic interruption, and a second game fixture. Studio's signed releases require separate signing verification; unsigned exported games require clear launch guidance. Existing focused Chromium and checkout-based Electron tests do not prove these packages. Each phase after the export proof should keep a buildable preview and locally built game slice.

Preview/export parity requires more than the same example appearing on screen. Pin the exported player/runtime build to the Studio preview build in the manifest and reject schema/runtime mismatches at export or build. Run identical command and state assertions on the five-scene and second fixtures in preview and cleanly extracted, independently built games on each claimed OS. Include scene transitions, inventory, dialogue, scripted failure, disabled-script nonexecution, save/load, and cinematic interruption. Compare durable snapshots and user-visible outcomes, while testing OS file paths, packaging, and signing separately. A fast one-target smoke build can run during intermediate stages; all three targets and full scenarios are the final gate.

## Goals vs. Non-Goals

* **In-scope goals:** code-checked replacement documentation outside `docs/design`; a dated source-of-truth and evidence map; an ordered RC plan; reusable scene navigation and durable session state; item definitions and inventory operations; JS-authored dialogue and sequences; scripted `.pcag` import trust choice with retained, visible disabled scripts; contextual actions with pending text; authored landing background, New/Load/Settings screen, volume and autosave settings, Exit return; local per-slot save files with tested fallback location; signed Studio distribution; unsigned game-project ZIP with local install/build script; the five-scene and second-fixture acceptance gates; preview/export parity; compatibility and failure behavior.
* **Out-of-scope non-goals:** visual node scripting, visual dialogue builder, website export with account management and database saves, a general crafting system, a general cutscene timeline editor, cloud publishing, multiplayer, and an assertion that a nontechnical person can author without code. Those remain separate release decisions or later work.

## Alternatives Weighed

1. **Keep the old programming-free first-release gate for this RC.** This preserves the previous promise, but the current editor lacks the required visual rules/dialogue tools and would expand the RC substantially. Carry that gate forward for a later independent-authoring release; label this RC technical. This is a proposed scope decision, not a claim of prior author approval.
2. **Delete all old docs at once, before writing replacements.** This gives a clean tree but loses accepted decisions, validation history, unique requirements, and external links during the rewrite. Stage replacement through inventory, fact extraction, new documents, and link checks; then delete the old files outside `docs/design`.
3. **Build a second game engine or new generic rule system.** The repository already has a shared Phaser runtime, action dispatch, movement, SceneManager events, worker scripts, and SceneState/GameState. Extend their contracts around one durable session and command boundary instead of duplicating them.
4. **Use app-close hooks as the only persistence mechanism.** App closure can interrupt a sequence or fail to finish a write. Commit explicit saves/autosaves at safe points and treat an unfinished cinematic as replayable.
5. **Treat the worker as a sandbox for arbitrary imported JavaScript.** `new Function` still has worker globals, and timeouts are an execution limit rather than a capability boundary. The chosen RC policy prompts on scripted `.pcag` imports and trusts folder projects. This trust choice must be enforced before any script runs; it does not isolate scripts from worker capabilities.
6. **Reuse the browser ZIP or export a PCAG-signed executable.** The current ZIP contains static web files, not a local Electron build project. Signing creator-authored scripts with PCAG's identity would misattribute the game. Export a versioned, rebuildable, unsigned game-project ZIP and let its build script fetch pinned dependencies, then let each creator sign their own game if they distribute it.
7. **Export an unsigned prebuilt game.** This would spare creators a Node/npm build and network dependency, but Studio would need separate OS/architecture game outputs or host-specific export, and creators would have less direct control over auditing and rebuilding before signing. The chosen source ZIP makes the build inputs visible and lets creators build/sign on their own target, at the cost of a documented local toolchain and build-script trust boundary.
8. **Save only beside the game or only in app data.** Game-folder files are easy to find and carry with a portable copy but can be unwritable. App data is writable by convention but less visible and can be left behind after relocation. Keep the chosen game-folder preference with a stable, visible fallback and deterministic handling when both contain slots.
9. **Build a visual sequence editor or broad inventory recipe framework now.** The acceptance story needs one ordered cinematic controller and narrow item commands. More general authoring can follow demonstrated need without changing the durable session contract.
